What this actually measures

A browser cannot send ICMP. No web API exposes raw sockets, so the ping command's actual protocol is unavailable to any web page. Each sample here is a real HTTPS request to the target — cache and credentials off, aborted at the timeout — and the figure is how long it took.

Does it agree with the ping command?

Mostly yes, and where it does not the reason is knowable. Measured on one machine, one network, the same minute:

HostICMP min / avgThis tool
carino.systems40.6 / 42.2 ms43 msagrees

cloudflare.com4.9 / 7.0 ms34 ms5×
www.cloudflare.com4.9 / 7.0 ms22 msbetter

The first two match ICMP to within a few percent. The third does not, and the measurement is not at fault: cloudflare.com/favicon.ico answers 301 and redirects to www.cloudflare.com. The browser follows it, so every probe pays a second request to a second host — a fresh DNS lookup, TCP handshake and TLS handshake on the first one, and an extra round trip on every one after. Probing the final URL directly cuts it from 34 ms to 22 ms.

So why is mine still higher than the terminal?

  • The target redirects. Check with curl -sI https://host/path. A 301 or 302 means you are timing two hops. Probe the URL it points at.
  • You are reading a total, not TTFB. Where a server sends no Timing-Allow-Origin header the browser hides the phase breakdown, so the figure is the whole request — including the server's own think time and the transfer. Those rows are marked total only. Rows marked TTFB are time-to-first-byte, which is mostly propagation delay.
  • ICMP and HTTPS may not talk to the same machine. An echo request is answered by the kernel of the first anycast node that sees the packet. An HTTPS request has to reach something that can actually serve the path, and on a CDN that can be a different machine in a different city.
  • The first request is not the steady state. It pays DNS plus the TCP and TLS handshakes — routinely three to five times the warm round trip, which is why Drop the first request is on by default: it is sent to open the connection and then not recorded at all. Turn it off and it is kept, shown on each card and in the exports flagged cold, and still excluded from every statistic on this screen.

STUN is a single UDP exchange with no TLS and no server-side work — the closest a browser gets to a raw round trip. It is the floor: what a target reads above it is protocol and application overhead, not distance. Downlink is measured before the run and never during it, because a saturated link has a full queue and a full queue adds delay to everything behind it.

The STUN exchange is the one probe that leaves for a host you did not name. It runs when you press Start or Test, never on page load, and it goes to . It returns your public address as a side effect — that is what a server-reflexive candidate is.

Why it cannot name your network interface

There is no web API for it, and that is deliberate rather than missing. Chrome and Firefox replace WebRTC host candidates with a random <uuid>.local name precisely so a page cannot enumerate the network it is on. navigator.connection.type is the nearest thing and only Chromium on Android and ChromeOS populates it; on desktop it is undefined, and Firefox and Safari do not ship the API at all. The Interface field reads not published rather than guessing from the effective type.

Other things worth knowing

IP addresses. A few answer — 8.8.8.8, 1.1.1.1 and 9.9.9.9 serve HTTPS with certificates valid for the address — but you are timing their web server, not the address's reachability. Most others have no HTTPS listener and come back unreachable, which says nothing about whether the host is up.

A 404 is a perfectly good round trip and is timed like any other reply, so the probe path does not have to exist. Some targets will log 404s in devtools; the measurement is unaffected.

Loss is counted, not hidden. A probe that times out or never connects increments loss and breaks the chart line, and a target that fails every request reads 100% loss rather than showing an empty graph.

Everything stays in this tab: targets and the client identifier are kept in this browser's local storage, samples exist only in memory until you export them, and no result is sent anywhere. The requests themselves obviously do reach the hosts you name.
